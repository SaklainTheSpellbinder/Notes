## Layer 1: Manual convolution via nested loops

This is the direct translation of the formula $y[n] = \sum_k x[k]h[n-k]$ into code — no shortcuts, so you can see exactly where every piece from Module 6 lands.

```python
import numpy as np

def manual_convolve(x, h):
    """
    x, h: 1D numpy arrays (or lists), assumed to start at index 0.
    Returns y = x * h, also starting at index 0, of length len(x)+len(h)-1.
    """
    N = len(x)
    M = len(h)
    L = N + M - 1          # output length, per the (N+M-1) rule from Module 6
    y = np.zeros(L)

    for n in range(L):                    # one iteration per output sample y[n]
        total = 0
        for k in range(N):                # k ranges over x's valid indices
            if 0 <= n - k < M:             # only count k where h[n-k] is in range
                total += x[k] * h[n - k]
            y[n] = total
    return y

# Example: reproduce the Module 6 worked example
x = np.array([1, 2, 1, 1])
h = np.array([1, 1, -1, 2])
print(manual_convolve(x, h))
```

Notice the `if 0 <= n - k < M` guard — this is _exactly_ the "check which pairs $(k, n-k)$ are valid" bookkeeping from Module 6's shortcut method. Run this, and you should get `[1. 3. 2. 2. 4. 1. 2.]` — the identical sequence we computed by hand in Module 6. **If your code and your hand-computation disagree, that's a strong signal you've mismanaged the index range somewhere — the exact same bug category as Module 6, Exercise 4's "spot the error" trap.**

### A subtlety worth flagging: what if your signal doesn't start at index 0?

Module 6, Exercise 3 had $x[n]$ starting at $n=-1$. Python arrays are always zero-indexed internally — they don't know or care what "time index" you intend a given array position to represent. So **you must track the starting index yourself, separately from the array**, and add it back on afterward:

```python
def convolve_with_offset(x, x_start, h, h_start):
    y = manual_convolve(x, h)
    y_start = x_start + h_start   # exactly the "starting index = sum of starting indices" rule
    return y, y_start
```

This directly implements the rule you _proved_ yourself in Module 6, Exercise 3 — the output's first valid index is the sum of the two inputs' first valid indices. Forgetting this offset bookkeeping is one of the most common sources of "my plot looks shifted wrong" bugs in a signals lab.

## Layer 2: Using `numpy.convolve` — and understanding its `mode` argument

You will almost never write the manual loop in practice (it's slow, and NumPy's built-in version is both faster and battle-tested) — but you need to understand _exactly_ what `mode` does, because this is the #1 source of confusion when comparing your hand-computed answer against code output.

```python
x = np.array([1, 2, 1, 1])
h = np.array([1, 1, -1, 2])

full = np.convolve(x, h, mode='full')   # default
same = np.convolve(x, h, mode='same')
valid = np.convolve(x, h, mode='valid')

print("full: ", full)
print("same: ", same)
print("valid:", valid)
```

**`mode='full'`** — this is the _entire_ convolution result, length $N+M-1$, exactly what Module 6 computes by hand. This is what you want if your lab asks you to "compute the convolution" in the textbook sense. Output: `[1, 3, 2, 2, 4, 1, 2]` — matches our hand computation exactly.

**`mode='same'`** — returns a result the _same length_ as the longer input (here, length 4, matching $x$), by trimming the "edges" (the low-overlap regions near the start and end) off the full result. This is often used in practice when you want the output aligned with the original signal's time axis (e.g., filtering an audio clip and wanting the output to be the same duration), but **it is not the mathematically complete convolution** — the trimmed-off edge samples are real, correct pieces of the answer, they're just being discarded for convenience.

**`mode='valid'`** — returns _only_ the samples where the two sequences fully overlap with **no zero-padding assumed on either side** — i.e., only the region where every term genuinely has both $x$ and $h$ available with no "missing" values treated as zero. This is the shortest output, length $\max(N,M)-\min(N,M)+1$ (here $4-4+1=1$; you'd get just the single sample $y[3]=2$, the point of full overlap identified in Module 6).

**The exam-relevant takeaway:** whenever your lab or CT asks you to "verify by code" a hand computation, use `mode='full'` — that's the one that corresponds to the actual convolution sum $\sum_k x[k]h[n-k]$ as derived in Modules 5–6 and 12. If your code output looks shorter than expected or doesn't match your by-hand answer, check whether you accidentally used `'same'` or `'valid'`.

## Layer 3: Verifying LTI behavior computationally — the "one impulse response predicts everything" promise, demonstrated in code

This is the piece that directly operationalizes Module 4's central claim. Let's actually _prove it to ourselves_ with code: measure a system's impulse response once, then show that convolving _any_ new input against that impulse response correctly predicts the system's true output — without ever "running" the input through the system's original definition again.

```python
import numpy as np
import matplotlib.pyplot as plt

# Suppose our "true" system is: y[n] = x[n] - 0.5*x[n-1] + 0.25*x[n-2]
# (a concrete LTI system, defined directly by its difference equation)

def true_system(x):
    """Runs an input through the ACTUAL system definition."""
    N = len(x)
    y = np.zeros(N)
    for n in range(N):
        y[n] = x[n]
        if n-1 >= 0: y[n] -= 0.5*x[n-1]
        if n-2 >= 0: y[n] += 0.25*x[n-2]
    return y

# Step 1: measure the impulse response by feeding in delta[n]
impulse = np.zeros(10)
impulse[0] = 1
h = true_system(impulse)
print("Measured impulse response h[n]:", np.round(h, 3))

# Step 2: pick a completely different, more complicated test input
x_test = np.array([2, -1, 3, 0, 1])

# Step 3a: get the output by running x_test through the TRUE system directly
y_true = true_system(x_test)

# Step 3b: get the output by CONVOLVING x_test with the measured impulse response h
y_via_convolution = np.convolve(x_test, h, mode='full')[:len(x_test)]  
# truncate to compare fairly against y_true's length, since h has extra trailing zeros

print("Output via true system:   ", np.round(y_true, 3))
print("Output via convolution:   ", np.round(y_via_convolution, 3))
```

If everything is implemented correctly, `y_true` and `y_via_convolution` should match (up to the length truncation, since our measured `h` array padded with extra zeros beyond where the true impulse response is actually nonzero). **This is the entire theoretical content of Modules 9–13, made tangible**: we measured the system's reaction to _one single_ input ($\delta[n]$), and then predicted its reaction to a _totally different_ input purely through convolution — never touching `true_system` again for the second calculation.

### Plotting, so you can visually confirm and present results (common lab requirement)

```python
fig, axs = plt.subplots(3, 1, figsize=(8,6), sharex=True)
axs[0].stem(x_test); axs[0].set_title("Input x[n]")
axs[1].stem(h[:len(x_test)]); axs[1].set_title("Impulse response h[n]")
axs[2].stem(y_true, linefmt='C0-', markerfmt='C0o', label='true system')
axs[2].stem(y_via_convolution, linefmt='C1--', markerfmt='C1x', label='via convolution')
axs[2].legend(); axs[2].set_title("Output y[n]: direct vs. convolution")
plt.tight_layout()
plt.show()
```

Overlaying the two output stems (direct system output vs. convolution-predicted output) and seeing them coincide exactly is a genuinely satisfying way to _see_ Module 4's promise hold up — this is a great thing to include in a lab report if you're asked to "demonstrate" or "verify" LTI behavior.

## Answers

**1.**

```python
x = np.array([2, 0, -1])
h = np.array([3, 1])
print(np.convolve(x, h, mode='full'))
# Output: [ 6  2 -3 -1]
```

This matches ${6,2,-3,-1}$ from Module 6, Exercise 1 exactly. ✓

**2.** When $x$ and $h$ have equal length $N$, `mode='valid'` returns an output of length $\max(N,N)-\min(N,N)+1 = N-N+1=1$ — just a **single value**. This single value corresponds to the _one specific sliding position_ where the reflected-and-shifted sequence lines up _exactly_ with the other sequence, edge-to-edge, with **complete, full overlap and no partial/zero-padded overlap at either end** — this is precisely the "$n=3$" moment from Module 6's worked example (where all four terms of both length-4 sequences lined up simultaneously), generalized to any equal-length pair. Everything else — the "ramping up" and "ramping down" partial-overlap output samples near the edges — gets discarded in `'valid'` mode, since those positions necessarily involve treating some values as implicitly zero (padding), which `'valid'` mode is specifically designed to exclude.

**3.** The buggy version is missing the **range-validity check** (`if 0 <= n-k < M`) entirely — it unconditionally computes `x[k] * h[n-k]` for every `k` from `0` to `N-1`, regardless of whether `n-k` actually falls within `h`'s valid index range `[0, M-1]`.

Two things can go wrong, depending on how Python/NumPy handles the out-of-range index `n-k`:

- If `n-k` is **negative**, Python's negative indexing (`h[-1]` means "last element of `h`") will silently return some _unrelated_ value from the _end_ of the array, rather than correctly treating it as zero — this corrupts the sum with a completely wrong extra term, without even raising an error, making it a particularly dangerous silent bug.
- If `n-k` is **too large** (≥ `M`), you'll get an actual `IndexError: index out of bounds` crash, since NumPy arrays don't automatically extend with implicit zeros beyond their defined length.

This is _exactly_ the conceptual mistake flagged in Module 6, Exercise 4: the student's code "writes out all terms and hopes the invalid ones vanish" — except in Python, invalid array indices don't just conveniently evaluate to zero the way $h[-1]=0$ does by mathematical _definition_ for signals; they either wrap around (silently wrong) or crash. This is precisely why the range-check `if 0 <= n-k < M` isn't optional bookkeeping — it's the code's way of enforcing the mathematical fact that $h[n]$ is _defined_ to be zero outside its stated range, which Python doesn't know unless you tell it explicitly.

**4.** (a)/(b) **Prediction first:** $x[n] = \delta[n] + \delta[n-3]$ means two impulses: one at $n=0$ (coefficient 1), one at $n=3$ (coefficient 1). By Module 12/13's bridge: each impulse produces its own shifted, scaled copy of $h[n]={1,0.5,0.25}$:

- From $\delta[n]$: copy of $h$ sitting at $n=0,1,2$ → values ${1, 0.5, 0.25}$
- From $\delta[n-3]$: copy of $h$ shifted to sit at $n=3,4,5$ → values ${1, 0.5, 0.25}$

Since these two copies occupy _non-overlapping_ index ranges (${0,1,2}$ vs. ${3,4,5}$ — no overlap because the second impulse arrives only after the first echo has already fully died out within our 3-sample truncation), there's no addition/interference between them — the predicted output is simply both echoes placed back-to-back: $$y[n] = {1,\ 0.5,\ 0.25,\ 1,\ 0.5,\ 0.25} \quad \text{for } n=0,1,2,3,4,5$$

**Code to verify:**

```python
h = np.array([1, 0.5, 0.25])
x = np.array([1, 0, 0, 1])
y = np.convolve(x, h, mode='full')
print(y)
# Expected: [1.   0.5  0.25 1.   0.5  0.25]
```

Running this confirms the prediction exactly — a nice concrete illustration of "two well-separated impulses just produce two independent, non-interfering copies of the impulse response," which is the cleanest possible visual demonstration of what convolution is actually doing.
